Procesamiento secuencial y paralelo de textos con Java Threads

Estudiante: Michael Lata Fecha: 8 de octubre de 2026 Repositorio: https://github.com/Whiteherobot/actividad01-java-threads

1.Descripción de la solución

El programa analiza Don Quijote de la Mancha (Project Gutenberg #2000) y cuenta el total de palabras, las apariciones de quijote y las palabras que contienen ción, sin distinguir mayúsculas. Tomé como palabra cualquier secuencia seguida de letras (Character.isLetter), así que las tildes y la ñ cuentan como letras. Antes de procesar quito el encabezado y la licencia de Gutenberg.

El código son cuatro clases: Contador cuenta las palabras de un rango del texto, HiloContador es el hilo, Resultado guarda los tres conteos y Main carga el libro, reparte el trabajo y mide. La versión secuencial llama a Contador.contar una vez con todo el texto, y cada hilo la llama con su parte, así ambas aplican el mismo criterio.

Para la descomposición de datos, el texto se divide en tantas partes como hilos. Si un corte cae dentro de una palabra, se mueve hasta el final de esa palabra:

JMain.java
src › actividad01 › Main.java › dividir
    /** Divide el texto en partes de tamaño parecido sin cortar ninguna palabra. */    static int[] dividir(String texto, int partes) {        int[] cortes = new int[partes + 1];        cortes[partes] = texto.length();        for (int i = 1; i < partes; i++) {            int corte = (int) ((long) texto.length() * i / partes);            // si el corte cae dentro de una palabra, se mueve hasta el final de esa palabra            while (corte < texto.length() && Character.isLetter(texto.charAt(corte))) corte++;            cortes[i] = corte;        }        return cortes;    }

Para la distribución del trabajo, cada parte se asigna a un HiloContador (que extiende Thread) y cada hilo guarda su propio resultado. Como los hilos no comparten datos que se modifiquen, no hace falta sincronizar. Se lanzan con start(), se esperan con join() y al final se suman los resultados. No se usa ExecutorService ni parallelStream().

JMain.java
src › actividad01 › Main.java › paralelo
    static Resultado paralelo(String texto, int numHilos) throws InterruptedException {        int[] cortes = dividir(texto, numHilos);        HiloContador[] hilos = new HiloContador[numHilos];        for (int i = 0; i < numHilos; i++) {            hilos[i] = new HiloContador(texto, cortes[i], cortes[i + 1]);            hilos[i].start();        }        Resultado total = new Resultado();        for (HiloContador hilo : hilos) {            hilo.join();            total.sumar(hilo.resultado);        }        return total;    }

Medición. El archivo se carga en memoria antes de medir. Con System.nanoTime() se mide solo el procesamiento: en la versión paralela entran la división, la creación de los hilos, el join() y la suma. Cada configuración se corre 3 veces de calentamiento (para el JIT) y luego 10 veces que se promedian. La versión ampliada repite el libro 100 veces. En cada ejecución el programa comprueba que el resultado paralelo sea igual al secuencial.

4.Análisis de resultados

  1. ¿Qué diferencias se observan entre los tiempos de ejecución secuencial y paralela? La versión paralela fue más rápida en todos los casos y dio los mismos conteos. En el ampliado el tiempo casi se divide entre el número de hilos (1.358 → 699 → 403 ms). En el original la mejora es menor (14,4 → 13,1 → 5,9 ms) y poco estable: con 2 hilos la aceleración fue 1,10 en una corrida y 1,55 en otra, porque con tiempos de 14 ms cualquier actividad del sistema influye.
  2. ¿Cómo influye el número de hilos en el rendimiento? Más hilos reducen el tiempo, pero solo hasta cierto punto. En el ampliado la eficiencia fue de 0,97 con 2 hilos y 0,84 con 4. Con más hilos la aceleración llega a unos 9× con 20 hilos y con 32 ya no mejora, porque el equipo tiene 20 hilos lógicos. Se aleja de la ideal porque solo 6 núcleos son de rendimiento: como las partes son iguales, el join() termina esperando a los hilos que cayeron en núcleos más lentos.
  3. ¿Qué sucede al incrementar el tamaño del documento? El tiempo secuencial crece casi en proporción al texto: 100 veces más texto tardó unas 94 veces más. La aceleración mejora: con 4 hilos pasó de 2,45 a 3,37. El costo de crear y coordinar los hilos es casi fijo, así que pesa mucho sobre 14 ms de trabajo y poco sobre más de un segundo.
  4. ¿El procesamiento paralelo siempre es más rápido? Justifique su respuesta. No. Con un fragmento de 2.000 caracteres el secuencial tardó 0,089 ms y el paralelo 0,277 ms con 2 hilos y 0,221 ms con 4, es decir, fue entre 2,5 y 3 veces más lento: casi todo el tiempo se va en crear y esperar los hilos. Tampoco mejora con más hilos que núcleos lógicos (32 contra 20). Además, según la ley de Amdahl, la parte que no se paraleliza (dividir, lanzar los hilos y sumar) limita la aceleración máxima.

5.Conclusiones

  • Dividir el texto en partes independientes sin cortar palabras permitió paralelizar solo con Thread, start() y join(), sin sincronización y con los mismos resultados que la versión secuencial.
  • El paralelismo conviene cuando hay suficiente trabajo por hilo: con el texto ampliado se obtuvo 1,94× con 2 hilos y 3,37× con 4, mientras que con un texto pequeño la versión paralela fue más lenta que la secuencial.
  • El número adecuado de hilos depende del hardware. Usar más hilos que hilos lógicos no ayuda, y en un procesador híbrido las partes iguales no aprovechan del todo los núcleos rápidos. Repartir el texto en partes más pequeñas que los hilos vayan tomando a medida que terminan podría equilibrar mejor la carga.
